    Verticalization Architecture - Country/WH Configuration Parameter Service (CPS) - internal

    • Created by Anne Brunn-Dürig on 21.08.2023

    • Motivation
    • Deployment
    • Data model changes
    • How to use the service
    • Changes
    • What if the service is not available?
    • Repositories

    Motivation

    The primary motivation is to enable FA to be deployed independently of physical access to the (so far shared) database tables T994 and T995 while allowing the domain to leverage the existing infrastructure (ie. the Admin Module) and libraries (eg. commons, cockpit) to smooth-lessly integrate with WFM's "country/wh configuration parameters."

    In the current "verticalisation 2.0" set-up, the CPS is part of each application. It [ie. CPS] uses the T994/T995 database tables as storage and, since embedded in each application, all clients/applications do directly access these. That's very unfortunate since this implies 1) all these applications to have these tables in their database and 2) actually share this database with each other — an application like food-campaigns uses/reads the configuration parameters, but has the admin application providing an editor for them. The long term vision is to decouple application from the direct usage of the database in respect to the mentioned tables and have them communicate exclusively through an abstracted API. The initial analysis of the state of "verticalisation 2.0" can be found here: Access of WH/Country Parameters from FA (mgm-internal only).

    Deployment

    1. config-param-api.jar: to be deployed to the FA, GRS, HLP clusters directly into Tomcat (shared classloader); part of the "remote api" jars, will eventually be deployed everywhere
    2. config-param-service.war: to be deployed to the GRS cluster
    3. ad-portlets.war: to be deployed to the HLP cluster
    4. fa-web.war and famd-web.war: to be deployed to the FA cluster
    5. in the GRS Tomcat the start up order has to give the new config-param-service a priority: -Dwfm.tomcat.startup.order=${STARTUP_ORDER:-gcs-service,config-param-service,...}  in bin/setenv.sh
    6. Default validation localizations under the "cps-service" bundle (in the localizer application) are to be reviewed/translated after deployment

    Data model changes

    None

    How to use the service

    • From a user perspective the synchronized parameters can be inspected via the REST end-points described by http://<HOST>/config-param-service/rest/api-docs
    • Otherwise, apart from the admin application, there's no interactivity with the service.
    • Coding against the new API: How to use the API (mgm-internal)
    • More detailed insights / thoughts are available in an informal style for mgm developers

    Changes

    None; this is the initial setup/release

    What if the service is not available?

    • FA applications will fail, these consider the service's availability as mandatory
    • The admin application will fall back to the old configuration service

    Repositories

    The new API and its accompanying implementation is split into three separate git repositories:

    • config-param-api: defines the API and the corresponding data transfer objects;
      • artifacts to be deployed to tomcats and being depended on as "provided"
      • changes expected to be rather rare here
    • config-param-service-parent: implements the service/api implementation itself
    • config-param-client-parent: provides client side utilities around "config params"
      • artifacts to be bundled as part of a client
      • artifacts to be depended on "compile" scope
      • changes expected rather more frequently as demand comes up from clients



    Future Improvements

    • Migrate all other modules towards the new API and fully deprecate the old API
      • Shared libraries: Commons (keys as well as support [eg. env] classes), Cockpit
      • Individual module applications
      • Database procedures
    • Full functionality coverage via the REST API – ie. read/write access
    • Persist Country/WH Configuration Parameter Definitions / Allow independent service restarts
    • Country/WH Configuration Parameter: Support key renaming and default value change
    • Support parameter value inheritance to warehouses when available on country level
    • Caching of parameter values to improve performance
    • Distributed, multi-instance service setup to provide fault tolerance
    • Provide a UI to allow editing warehouse parameters; currently, the admin offers an editor for country parameters only
